# PR #16 review follow-ups (deferred)

Confirmed-but-deferred items from the SWE-agent review of https://github.com/Pipelex/pipelex-sdk-js/pull/16. Each was verified against the code; they are deferred because they need a design decision or more context than a PR-review pass should unilaterally resolve — not because they are wrong. (The base64 finding from the same review was confirmed and fixed in the PR; it is not listed here.)

## 1. Browser bundling of `@pipelex/sdk` fails on `node:fs/promises` — DECIDED: Node-first

- **Decision (2026-07-22): Node-first. Do not build browser/edge packaging now.** Surveyed the three real consumers — `pipelex-starter-js` (Next.js: SDK runs in Server Actions / `src/lib`, Node runtime, no `"use client"` SDK import, no edge runtime), `pipelex-mcp` (SDK confined to the Node MCP server in `src/capabilities`; its Vite/React `src/views` import zero SDK code), and `pipelex-plugins` (SDK consumed only via a pre-built esbuild `platform:node` hook bundle). **None bundle the SDK for the browser, and none exercise the upload/`node:fs` path.** So the packaging fix (option c) would protect a target nothing exercises — deferred indefinitely, not built. The `readLocalPath` comment fix (this PR) plus the docs caveat in [`docs/input-preparation.md`](../docs/input-preparation.md) are the whole resolution. **Revisit trigger:** the first browser client-component import or Next.js edge-route import of the SDK — then do option (c) with a bundle-smoke test.
- **Reporter:** greptile-apps (P1) — [thread](https://github.com/Pipelex/pipelex-sdk-js/pull/16) on `src/upload.ts` (~line 109, `readLocalPath`).
- **Issue:** `readLocalPath` does `await import("node:fs/promises")` with a static string literal, runtime-guarded by `isNodeRuntime()`. But the module is statically reachable from the package entry (`src/index.ts` → `client.ts` → `upload.ts`; `prepare-inputs.ts` too), so a browser-targeting bundler resolves the literal specifier at build time regardless of the runtime guard, and any bundler that rejects Node built-ins for browser targets fails to build **any** `@pipelex/sdk` consumer — including callers that only ever upload `Blob`/byte values and never reach `readLocalPath`. The guard governs execution, not bundling.
- **Confirmed empirically:** esbuild 0.25.12 `--platform=browser --bundle` on a byte-only entry → `✘ Could not resolve "node:fs/promises"`. `--platform=browser --bundle --external:node:*` builds OK; `--platform=node` builds OK (control). Magic comments (`/* @vite-ignore */`, `/* webpackIgnore: true */`) do **not** help — esbuild ignores them.
- **Why deferred (needs-judgment):** browser/edge is *documented* ([`docs/input-preparation.md`](../docs/input-preparation.md):9,19 — byte sources are "Accepted sources (every runtime — browser, Node, edge)") and *coded-for* (`bytesToBase64`'s `btoa` fallback, `prepare-inputs.ts`'s `atob`/`base64ToBytes`, `readLocalPath`'s "pass the file as bytes" message), but it is **not packaged or tested**: `package.json` has no `browser` field, no `browser`/`worker`/`edge-light` `exports` condition, a single `.` export → `dist/index.js`; the repo neither builds nor tests any browser bundle (the only esbuild use, `scripts/build-hook.mjs`, is `platform: "node"`). So the promise exists at the API level but is unbuilt at the packaging level. The right fix depends on whether browser is a first-class build target — a decision the SDK owner should make, not a PR-review pass.
  - As a stopgap, the false comment on `readLocalPath` (which claimed the dynamic import "never lands in a browser bundle") was corrected in this PR to state the real bundling caveat and point here. No behavioral change.
- **Options (decide the target first, then pick):**
  - **(a) Runtime-computed specifier** — `const spec = "node:fs" + "/promises"; await import(spec)`. Minimal (~2 lines); empirically makes esbuild/Vite/Rollup browser bundles build. But it is a static-analysis-defeating hack, only *partial* (webpack `target:web` still needs `resolve.fallback` config), and unverified without a browser bundle-smoke test — risk of false confidence.
  - **(c) `exports` `browser`/`node` conditions + a browser stub `readLocalPath`** (that throws `InvalidLocalSourceError`) — the universal, solid fix: the browser condition never references `node:*`, so every bundler is satisfied. Heavier (a second module + packaging surface). Warranted **only** once browser is a committed target **with a CI bundle-smoke test** — otherwise it protects a target nothing exercises.
  - **(d) Leave as-is + document "mark `node:*` external"** — a reasonable stance for a Node-first SDK, but it must be reconciled with the current "every runtime — browser, Node, edge" docs claim (the runtime claim is true; the bundling caveat is what's missing).
- **Resolution (option d, chosen):** keep the byte fallbacks as runtime niceties and document the Node-first packaging stance (done — `docs/input-preparation.md` "Runtime acceptance vs. bundling" caveat). Option (a) alone was rejected as an untested partial hack; option (c) is the right fix *if/when* the revisit trigger fires, paired with a CI bundle-smoke test. PR thread resolved with this decision recorded.
