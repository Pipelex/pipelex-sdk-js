# PR #35 review triage — deferred item and dismissed findings

Triage of the unresolved bot threads on [PR #35](https://github.com/Pipelex/pipelex-sdk-js/pull/35), the release PR for v0.14.0. Greptile, Codex and cubic all reviewed the same commit. Nine threads reduced to six independent findings: three were real inaccuracies in prose and were fixed on the branch, three were false positives, and one is confirmed but belongs to a decision already escalated out of this repo.

The three that were fixed needed no note: `docs/crate-routes.md` claimed the published package runs `lint`/`format` offline through `@pipelex/tools-wasm`, which is true of the vendored hook bundle and not of `npm install @pipelex/sdk` — corrected there, in the matching `CHANGELOG.md` line and in the crate-extensions comment in `src/client.ts`; the `TODOS.md` follow-up entry still said prod crate exposure was awaiting a deploy, contradicting the note it links to; and `wip/validation-error-item-drift.md` recorded its closure as "following the three steps above" when step 3's live-wire half was never attempted.

## Deferred: a non-string `method_id` from untyped JavaScript is silently dropped

**Reporters:** `greptile-apps`, `chatgpt-codex-connector` and `cubic-dev-ai`, independently, all three on the same finding.

**This is the PR #34 item, re-raised.** It is confirmed, and it was already triaged and deferred once — the reasoning, the mechanics, and the reason a `method_id`-only guard is the wrong shape of fix are all recorded in [`wip/pr-34-review-notes.md`](./pr-34-review-notes.md) § 1. The open question it turns on — whether the SDK stack runtime-checks request-option types at its public package boundary — spans this package, `mthds`, `pipelex-sdk-python` and `mthds-python`, and is filed at the workspace level as `wip/inbox/2026-08-24-workspace-sdk-runtime-option-validation.md`. Cubic's proposal on this PR (validate every public option: strings for `method_id` / `bundle_b64` / `pipe_code`, a string map for `files`, a string array for `mthds_contents`) is already written down there as the "yes" branch of that question.

Nothing new was learned this round, with one exception worth recording so the next reviewer does not have to derive it again: **the fully-silent outcome is narrower than all three bots describe.** The run-source precondition (`src/client.ts:550-560` for `execute`, `:614-624` for `start`) counts hosted extension keys, so a wrong-typed `method_id` supplied *alone* fails the precondition and throws — the caller gets an error, merely a confusing one. Silence requires a wrong-typed `method_id` alongside a valid inline source, where the consequence is a permanent absence from `GET /v1/runs?method_id=`.

Deliberately not fixed on a release branch: the reachable path requires a caller already ignoring the published types, and landing new throwing behaviour after the v0.14.0 changelog was written, for one field out of five sharing the same exposure, would leave the surface less coherent than it is now. The three threads are left open pointing here.

## Dismissed, with the reasoning, so they are not re-litigated

**The blocking-fallback test in `tests/client.test.ts` — flagged by cubic on two consecutive PRs, on different and both incorrect grounds.** On PR #34 cubic read `fetchSpy.mock.calls[1]` as out of bounds; on PR #35 it read the test as not exercising the fallback because `implementation: "pipelex-api"` steers to `executeBlocking()` immediately. That steering is the point: `src/client.ts:243` declares `"pipelex-api"` as `BARE_RUNNER_IMPLEMENTATION`, the bare open-source runner with no run store, and the test is named for that branch. `startResponse()` is not mocked in this test at all — it is a sibling helper used by four other tests in the block. The test self-verifies by asserting the second fetch is `/v1/execute`, so a mis-steered handshake would fail loudly. The hosted-404 sequence cubic proposed already exists as its own test, `tests/client-lifecycle.test.ts` § "self-heals when a base-only version response hides a missing run store"; adopting the suggestion would have duplicated it and lost the bare-runner coverage.

**The `input_form` assertion in `tests/e2e/tools.e2e.ts`.** Cubic read the 0.17.0 mentions in `docs/architecture.md`, `src/models.ts` and `src/client.ts` as naming the runner the e2e suite targets. They do not — they explain why `PipelexValidationReport.input_form` is typed optional rather than required, which is a statement about tolerating an old body, not about what the current server sends. `pipelex-api` 0.18.0 gates the field on the `views` token, its own unit suite pins the identical assertion, and the workspace spec `docs/specs/mthds-input-form-descriptor.md` states the field is absent by default. Accepting both response shapes would have made all three new assertions vacuous against exactly the regression they exist to catch.

**Re-adding the superseded 2026-08-13 measurement to `wip/hosted-exposure-crate-and-tools-routes.md`.** Cubic attributed this to team feedback about preserving dated hosted measurements; no such convention exists in any `CLAUDE.md` or doc in this repo or the workspace. The written intent is the opposite — [`wip/crate-routes-resume.md`](./crate-routes-resume.md) planned for this moment: "When prod ships, the remaining edit is small: drop the prod row from each." The dated evidence that explains something is retained in the note's "The gap (as originally found)" section; what was dropped is which hosted version each origin happened to run on one Thursday, which is the volatile state the workspace guide says never to write down, and which git holds verbatim regardless.
